5 Platform, product taxonomy, and task bank

The experiment needs a controlled storefront, a task generator, and an event log precise enough to reconstruct every path. This section specifies the product set, the task design, the success criteria, the logging schema, and the build-versus-reuse choices. The goal is a platform that a second researcher can reproduce from a repository and a seed.

5.1 The fictional store

The store is called Meridian Timepieces (fictional; no real brand, logo, or trademark). It sells 72 watches across four departments. Product images are either generated 3D renders or licensed stock images with brands removed; all prices are fictional. The visual design is deliberately clean and consistent across conditions: white background, slate text, teal accent, four department colours used as redundant cues. The same product detail page is used after a correct selection in every menu, so the post-selection experience cannot explain differences.

Each leaf style is assigned a unique attribute vector. A build-time test checks that every target description maps to exactly one product; if two products share the same description, the task is rejected and regenerated. This prevents ambiguous “find the blue watch” tasks from contaminating the design.

5.2 Task design

The primary task is known-item product finding: the participant is given a short, natural-language shopping goal and must reach the correct product detail page using the menu. The task never names the exact product; it describes two or three attributes. This forces category navigation rather than string matching, while keeping the target unambiguous.

Example task (the running example)

“You’re looking for a titanium dive watch with 300 m water resistance and a deep blue dial. Find it.”
Correct path: Sport & Dive → Pro Diver 300m → Steel Blue (or the leaf whose attribute vector matches; the build-time uniqueness test decides). The exact label “Titanium Deep” is not shown in the task, so the participant must use the hierarchy and the product attributes.

Difficulty is manipulated as a within-participant covariate, not as a fully crossed factor. Three levels are defined by three orthogonal properties: (1) serial position of the department and subcategory in the menu, (2) semantic distance between the task wording and the leaf label, and (3) number of plausible distractor leaves with the same colour or material. Each participant sees 24 targets, balanced 8 easy / 8 medium / 8 hard. The assignment of difficulty to the 24 menu × state cells is rotated across participants so difficulty cannot be confounded with a condition.

5.4 Event logging and data schema

Every interaction is logged as a JSON line with a client timestamp (performance.now()) and a server receipt timestamp. The client timestamp is used for within-trial timing; the server timestamp is used for data integrity. Events are batched every 500 ms and flushed on page unload; an offline queue prevents data loss if the connection drops.

5.5 Platform architecture

The recommended build is a single-page React + TypeScript application with a small Node/PostgreSQL backend. The front end owns the menu renderers, the experiment timeline, and the event buffer. The back end owns randomisation, condition assignment, data ingestion, and exports. The analysis pipeline reads a versioned CSV/JSONL export and a frozen analysis script.

5.7 Accessibility and standardisation

All menus should meet WCAG 2.2 AA where feasible: keyboard operability, visible focus, 4.5:1 text contrast, 3:1 non-text contrast, reduced-motion support, and semantic roles. However, the confirmatory experiment standardises on mouse/trackpad to compare motor performance; keyboard input is supported and logged, and participants who prefer it are not excluded. Input modality is included as a covariate, and a separate accessibility session can be run if the sample includes keyboard-only users. Do not claim full accessibility compliance without an audit.

Build acceptance criteria (gate to pilot)

  • Every one of the 72 products is reachable in every menu, with the same number of semantic levels.
  • Every target description maps to exactly one product (uniqueness test).
  • All six menus show the same labels and product data from one JSON source.
  • All interactive targets are ≥ 44 × 44 px at 1920 × 1080; no overlap or clipping.
  • Transitions are 180–220 ms and do not drop below 50 fps on the lab machine.
  • Event logs reconstruct the full path for 100% of test trials; no missing trial_end.
  • Randomisation is reproducible from a seed and audited server-side.
  • No console errors; no external network requests during a trial.

6 Study design overview

The programme is sequential by design. Study 1 estimates the mapping; Study 2 freezes it and tests causality; Study 3 tests the complete system with a noisy estimator. This avoids the circularity of deriving a policy and testing it on the same data.

6.1 Why three studies rather than one

DesignWhat it can showWhat it cannot show
Single 6 × 4 experimentWhether menus differ across induced states; a descriptive mapping.Whether using the mapping causally helps; whether switching costs erase the gain; whether a noisy estimator works.
Single adaptive-vs-static experimentWhether an adaptive system beats a static one.Whether the benefit comes from matching, from change/novelty, or from a better global menu.
Three-study sequenceMapping, causal matching, and end-to-end feasibility, each with a clean counterfactual.Long-term learning and real-world adoption; those are future work.

6.3 Randomisation and counterbalancing

Study 1 has two crossed order factors: four emotion blocks and six menus within each block. A full randomisation of 24 cells would confound order with the cell-specific targets at small N. Instead, use two Latin squares:

  • Emotion block order: four sequences — ABCD, BCDA, CDAB, DABC — assigned evenly across participants. Each state appears in each serial position exactly once across the four sequences.
  • Menu order within block: a 6 × 6 balanced Latin square, so each menu appears in each within-block position once. A different row is used for each block to avoid the same menu always following the same state.
  • Target rotation: six target sets of 24 tasks, each balanced by department and difficulty. Across participants, each target set is paired with each block order and menu order equally often. The full matrix is in Appendix E.
  • Practice: one practice trial per menu (not analysed) before the main blocks, to separate menu learning from the experimental effect. Practice targets are not reused in the main trials.
  • Breaks: a 2-min neutral reset between blocks; participants can take a longer break without losing compensation.

Study 2 uses the same block-order logic but four conditions per state. The four conditions are presented in a 4 × 4 Latin square within each block; across participants, each condition appears in each position equally often. Study 3 has two conditions (static, hybrid) and uses an ABBA/BAAB crossover to balance order and carry-over.

6.5 Recruitment, inclusion, and compensation

Recruit adults aged 18–65 who are fluent in English and have normal or corrected-to-normal vision. No prior participation in the pilot or in another study of the programme. Colour vision is screened with a short Ishihara-style test; the palette is designed to be distinguishable for the most common deficiencies, so colour-vision deficiency is not an automatic exclusion — it is recorded and analysed as a covariate. Participants must be able to use a mouse or trackpad; keyboard-only users can be accommodated in a separate session.

Use a university participant pool and a reputable online panel (e.g., Prolific) for the reduced design. Compensate at £12–£15 per hour or course credit with a comparable alternative. Do not use performance-contingent bonuses: they would confound emotion induction and risk pressure. Target a 20% attrition/technical-failure buffer; replace participants who fail the pre-registered data-quality checks, not those whose results are inconvenient.

Stopping and data-quality rules

Collect in waves (e.g., 4 × 18 participants in Study 1) and check only data quality between waves: missing logs, failed randomisation, session length, and technical errors. Do not check condition effects or stop early for significance. Pre-register the final N. Exclude a session only if (a) the event log is incomplete for more than 10% of trials, (b) the participant did not complete at least 75% of trials, (c) the participant reports a technical failure that prevented menu use, or (d) the participant was previously in the pilot. Report all exclusions and the reasons in a flow diagram.
