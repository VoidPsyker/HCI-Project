14 Implementation plan

This section is the build contract for the prototype. It assumes a small team (one developer plus one researcher) and a six-week build before the pilot. The goal is not a production e-commerce site; it is a controlled, reproducible instrument that can run six menu architectures over one taxonomy and produce analysis-ready logs.

14.1 Architecture

14.2 Shared taxonomy and the renderer contract

The single most important engineering decision is to make the taxonomy a single source of truth. Every menu renderer reads the same JSON tree and emits the same event vocabulary. A change to a label or a product must propagate to all six menus or fail the build.

export type MenuId = "A" | "B" | "C" | "D" | "E" | "F";

export interface MenuNode {
  id: string;                 // stable, e.g. "sport.prodiver.titanium"
  label: string;
  level: 1 | 2 | 3;
  parentId: string | null;
  productId?: string;          // only for leaves
  colour?: string;             // department colour token
  icon?: string;               // icon name, same across menus
}

export interface MenuRendererProps {
  menuId: MenuId;
  nodes: MenuNode[];
  visibleLevel: 1 | 2 | 3;
  onOpen: (nodeId: string) => void;
  onSelect: (nodeId: string) => void;
  onBack: () => void;
  log: (event: LogEvent) => void;
  disabled?: boolean;
}

export interface MenuRenderer {
  mount(el: HTMLElement, props: MenuRendererProps): void;
  update(props: Partial<MenuRendererProps>): void;
  destroy(): void;
}

Each menu is a separate component that implements this contract. The runner mounts one renderer at a time and logs every open/select/back event with the same schema. The taxonomy package also exports a validateTaxonomy() function that checks: four departments; three L2 per L1; six L3 per L2; unique IDs; unique product descriptions; no orphan nodes.

14.3 Randomisation service

Randomisation is server-side and auditable. The service pre-generates balanced sequences from a seeded PRNG and assigns each participant to the next sequence in a stratified block. The client never chooses a condition. The audit table stores the sequence ID, block order, menu orders, target set, and a hash of the seed.

// Pseudocode — server-side assignment
sequences = generateBalancedDesign({
  blockOrders: latinSquare(4),      // ABCD, BCDA, CDAB, DABC
  menuOrders: latinSquare(6),       // 6 × 6
  targetSets: 6,
  seed: CONFIG.seed
});

onJoin(participant):
  stratum = stratify(participant.gender, participant.shoppingFrequency)
  seq = nextUnused(sequences, stratum)
  audit(participant.id, seq.id, hash(CONFIG.seed))
  return seq

Balance checks run nightly: each block order, menu position, and target set should be used with approximately equal frequency. If a stratum is exhausted, generate a new block rather than reusing sequences. Any deviation is logged and reported in the paper’s supplementary materials.

14.4 Adaptation engine

The engine is deliberately conservative. It runs at task boundaries, uses a calibrated posterior, and abstains when uncertain. The pseudocode below is the specification for Study 3; Study 2 uses a frozen policy with known labels and no estimator.

onTaskBoundary(participant, currentMenu):
  features = extractFeatures(participant.recentTrials)
  prior = participant.blockCheckin          // 1-item state prior
  posterior = estimator.predict(features, prior)
  state = argmax(posterior)
  confidence = max(posterior)

  if confidence < 0.70:
      log("no_adaptation", reason="low_confidence")
      return currentMenu

  target = policy[state]
  gain = expectedUtility(target, state) - expectedUtility(currentMenu, state)

  if gain < MIN_GAIN or dwell < 2 or recentSwitch:
      log("no_adaptation", reason="guardrail")
      return currentMenu

  showBanner(target, reason="support_current_task")
  if user.keepsCurrent:
      log("adaptation_rejected")
      return currentMenu

  log("adaptation_accepted", state, confidence, gain)
  return target

The engine logs every decision, including abstentions. This is essential for the analysis: a system that adapts rarely but well is different from one that adapts often and badly, even if their average task performance is similar.

14.6 Deployment, security, and data handling

  • Lab deployment: a wired local server, Chrome/Edge kiosk mode, full-screen 1920 × 1080, no internet during a trial. The database runs on the same machine or a local network host; daily encrypted backups to a separate drive.
  • Cloud option: a managed Postgres (EU region) and a static front end behind authentication; a data-processing agreement; no third-party analytics or advertising scripts.
  • Security: HTTPS, content-security policy, no third-party scripts, rate limiting, parameterised queries, least-privilege DB roles, secrets in environment variables only (never in the repo).
  • Privacy: pseudonymous participant IDs; no names, emails, or IP addresses in the research dataset; a separate encrypted key linking IDs to consent forms; retention according to ethics approval (e.g., 5 years) and deletion thereafter.
  • Audit: every randomisation and adaptation decision is written to an append-only audit table; the raw event stream is archived as JSONL with a checksum.

14.8 Reproducibility package

Use a monorepo with apps/web, apps/api, packages/taxonomy, packages/analysis, and docs/. Commit lockfiles, a Docker Compose file, a .env.example (no secrets), and a README that a new researcher can follow from a fresh clone to a running local session. Version the taxonomy and store its hash with every session. Archive the analysis script and a session-info file with the manuscript; deposit the anonymised data and materials in a repository with a DOI if ethics allow.

Build risk register

Custom geometry takes longer than expected: prototype D/F in week 1 with static SVG before wiring interactions. Browser performance: test 60 fps early; avoid heavy DOM for the mega panel. Data loss: offline queue plus nightly backup; test a network drop. Randomisation bug: server-side audit and a dry-run balance check. Accessibility debt: keyboard tests from week 2, not at the end.
